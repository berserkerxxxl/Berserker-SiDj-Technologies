# СиДжи — Telegram webhook на Cloudflare Workers

Worker заменяет пятиминутный опрос командами через webhook. Уведомления о сборках и обновлениях остаются в отдельном GitHub Actions workflow. Код подготовлен к развёртыванию; сам факт наличия файлов в GitHub ещё не означает, что бот переключён.

Если авторизация в облачном браузере не работает, подготовлен [сценарий через GitHub Actions](GITHUB_ACTIONS_RU.md). Он использует ограниченный API-токен из GitHub Secrets, не требует входа агента в Cloudflare Dashboard и запускается только вручную.

## Развёртывание через Cloudflare

1. Войти в Cloudflare и проверить **Workers Free**. Платный план, платные дополнения, R2, KV, D1, Queues и Durable Objects для этой версии не нужны. Если аккаунт уже платный, сначала проверить его условия; конфигурация Wrangler сама не переводит аккаунт на Free.
2. Workers & Pages → создать Worker из GitHub. Дать приложению Cloudflare доступ **только** к `berserkerxxxl/Berserker-SiDj-Technologies`, а не ко всем репозиториям. Отдельный GitHub PAT для работающего бота не требуется: каталог и Actions читаются из публичного репозитория.
3. Выбрать `main`, папку `cloudflare/sidj-worker`, имя **`bs-tech-sidj`**. Команда сборки: `npm ci --ignore-scripts && npm run check && npm test`. Команда развёртывания: `npm run deploy`. Node.js 24. Закреплённая версия Wrangler и package-lock.json обеспечивают воспроизводимость зависимостей.
4. После первого развёртывания записать точный адрес `workers.dev`. В Settings → Variables and Secrets добавить:

| Имя | Тип | Значение |
| --- | --- | --- |
| `SIDJ_TELEGRAM_BOT_TOKEN` | Secret | Действующий токен именно `@BS_SiDj_bot` |
| `SIDJ_TELEGRAM_CHAT_ID` | Secret | Положительный числовой ID личного чата владельца |
| `SIDJ_ADMIN_TOKEN` | Secret | Отдельный случайный пароль панели, 32–128 символов `A–Z a–z 0–9 _ -` |
| `SIDJ_PUBLIC_URL` | Text | Точный `https://…workers.dev/`, без дополнительных путей, query и fragment |

Секреты вводятся только в защищённом интерфейсе. Токен бота и пароль панели не помещаются в чат, GitHub, URL или wrangler.toml. `SIDJ_ADMIN_TOKEN` не является токеном Telegram.

5. Применить настройки через Deploy. Открыть `/setup` на точном адресе Worker. Панель не сохраняет пароль в localStorage/sessionStorage; после запроса поле очищается. Операции доступны только с Bearer-паролем и на каноническом origin. Старый публичный GET `/activate` больше ничего не переключает.
6. Сначала выполнить «Проверить подключение». Панель проверит имя бота и личный чат. Затем провести переключение по разделу ниже.

## Переключение без потери очереди

1. Оставить `sidj-telegram-commands.yml` включённым. `sidj-telegram-notify.yml` тоже остаётся включённым.
2. Убедиться, что запущенный job старого опроса уже закончился. Это уменьшает риск, что одна команда попадёт в момент перехода обоим обработчикам.
3. В `/setup` нажать «Подключить webhook». Передаётся только заранее заданный адрес `/telegram`, `max_connections=1`, типы `message` и `callback_query`; `drop_pending_updates=false` сохраняет очередь. Чужой существующий webhook не перезаписывается. Повторная активация обновляет секрет заголовка даже при прежнем URL.
4. Проверить `/start`, `/help`, `/projects`, `/project reserve`, `/download`, `/status`, `/builds`, `/errors`. Нажать каждый проект, кнопку возврата и загрузки. Получить небольшой JS/HTML/EXE, проверить имя и SHA-256; отдельно проверить ZIP B/S Reserve и ссылку Linux.
5. Проверить отказ на POST `/telegram` без секретного заголовка, а также отсутствие ответа в чужом чате/группе. Секрет заголовка вычисляется из токена бота, в публичный URL не попадает. Одного совпадения ID чата недостаточно — проверяется также ID отправителя и `is_bot=false`.
6. В Cloudflare проверить CPU, ошибки, фактическое время ответа; в `/setup` — состояние webhook и очередь. Синтетический тест и локальный dry-run не заменяют эту проверку.
7. **Только после успешных реальных проверок** отключить расписание/сам workflow `sidj-telegram-commands.yml`. Скрипт опроса уже автоматически выходит, если webhook установлен; отдельно обработана гонка включения webhook между проверкой и `getUpdates` (HTTP 409).
8. `sidj-telegram-notify.yml` не отключать: он отправляет уведомления и не читает `getUpdates`, поэтому не конкурирует с Worker.

При обычной успешной сборке бот показывает короткий итог без ссылок. При ошибке — название неуспешного задания/шага и кнопку «Посмотреть ошибку». Историческим сборкам не приписывается версия текущей публикации. При недоступности GitHub бот сообщает об этом, а не утверждает, что ошибок нет. Данные кэшируются до 60 секунд.

## Файлы и контроль целостности

- Все 8 текущих файлов имеют `sha256` и `size_bytes` в `automation/sidj_projects.json`. `files_ref` закрепляет их за конкретным Git-коммитом: содержимое ссылки не меняется при следующих обновлениях `main`.
- Небольшие файлы (до 1 МиБ) Worker читает с потоковым ограничением размера, сверяет длину и SHA-256, затем отправляет multipart-вложением. Отсутствие или неверный Content-Length не позволяет обойти лимит. При несовпадении передача отменяется, обходная ссылка не выдаётся.
- Крупные ZIP/PDF до **20 000 000 байт** Telegram скачивает самостоятельно по HTTPS из неизменяемого Git-коммита. В памяти Worker архив не собирается; в подписи указывается SHA-256 опубликованной версии, проверенный при подготовке каталога. Повторное хеширование большого архива в Worker не выполняется. GitHub отдаёт текущие ZIP с `Content-Type: application/zip`.
- Для `.tar.gz`, более крупных файлов и отклонённой отправки предлагается только ссылка из каталога на закреплённый коммит и ожидаемый SHA-256. Это не утверждение, что скачанный по ссылке файл уже проверен на устройстве пользователя.
- Лимит multipart в Telegram — до 50 МБ; более низкий порог Worker выбран для CPU/памяти бесплатного тарифа. Загрузка ZIP по URL имеет отдельный лимит Telegram 20 МБ и ограничения формата/MIME.
- Произвольные URL, обходы `..`, другие каталоги и callback_data длиннее 64 байт не принимаются. Каталог встроен в сборку как запасной вариант при сбое GitHub.

После публикации новых бинарных файлов сначала закоммитить их, затем выполнить из корня репозитория:

```bash
python3 automation/update_sidj_catalog.py --ref HEAD
python3 automation/update_sidj_catalog.py --check
```

Закоммитить обновлённый каталог. Скрипт вычисляет SHA-256/размер по указанному коммиту и сверяет sidecar-файлы архивов; незакоммиченные бинарные файлы не подставляются в закреплённую ссылку.

## Доставка и ограничения

Обработка команды и отправка ответа ожидаются **до** HTTP 2xx; при сбое Telegram может повторить доставку. Основная работа не запускается через fire-and-forget `waitUntil`. Повтор одного update объединяется и запоминается в текущем изоляте. Этот кэш не является долговременной/глобальной базой: после перезапуска, переноса в другой изолят или потери ответа Telegram редкий повтор сообщения возможен. Гарантия exactly-once не заявляется.

Workers Free: 100 000 входящих запросов в сутки на аккаунт, CPU 10 мс на запрос, память 128 МБ, до 50 подзапросов. Сеть не считается CPU. Крупные файлы не буферизуются; число workflows в каталоге ограничено. Новая версия не создаёт платных хранилищ или очередей. Реальные CPU и тариф аккаунта требуется проверить после авторизации; превышение квоты Free не является согласием на платный тариф.

## Откат и смена токена

Перед откатом включить старый workflow, если он уже выключен. В `/setup` выбрать «Откатить на опрос»: удаляется только webhook этого Worker с `drop_pending_updates=false`. Старый workflow вернётся к опросу на ближайшем запуске. Уведомления сохраняются.

Если токен был скомпрометирован, владелец отзывает его в официальном BotFather и вводит новый непосредственно в Cloudflare Secret **и** в одноимённый GitHub Actions Secret `SIDJ_TELEGRAM_BOT_TOKEN`. Сначала готовится развёртывание и оба интерфейса секретов, затем выполняется смена: отзыв старого токена неизбежно делает его недействительным, поэтому нулевой перерыв при ротации не гарантируется. После применения нового токена нужно повторно активировать webhook; это обновит проверяемый заголовок. ID чата в обоих сервисах должен совпадать. Не пытаться извлечь или показывать сохранённые секреты GitHub.

## Локальные проверки без настоящих секретов

```bash
cd cloudflare/sidj-worker
npm ci --ignore-scripts
npm run check
npm test
npm run deploy:check
```

Из корня репозитория:

```bash
python3 -m unittest discover -s automation -p 'test_sidj_telegram.py' -v
python3 automation/update_sidj_catalog.py --check
python3 automation/check_sidj_secrets.py
```

CI `sidj-worker-checks.yml` выполняет эти проверки без секретов и без развёртывания. Сканер выводит только пути/строки и распознаваемые шаблоны Telegram/GitHub; он не гарантирует отсутствие произвольных секретов и не проверяет изображения/историю аккаунта.

Официальная документация: [лимиты Workers](https://developers.cloudflare.com/workers/platform/limits/), [тарифы Workers](https://developers.cloudflare.com/workers/platform/pricing/), [Telegram Bot API](https://core.telegram.org/bots/api).
