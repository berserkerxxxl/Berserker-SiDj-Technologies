# Подключение Cloudflare через GitHub Actions

Запасной путь, когда вход в Cloudflare из облачного браузера не завершается. Cloudflare API используется только после ручного запуска workflow; расписания и автоматического переключения webhook здесь нет.

## Что один раз делает владелец

1. В своём обычном браузере войти в Cloudflare. Проверить **Workers Free** и наличие поддомена `workers.dev` в разделе Workers & Pages. Если поддомен ещё не выбран, завершить бесплатное начальное подключение Workers в интерфейсе Cloudflare. Соглашения принимает сам владелец.
2. В профиле Cloudflare открыть **API Tokens → Create Token → Create Custom Token**. Название: `BS-tech-SiDj-deploy`. Право: **Account → Workers Scripts → Edit**. В Account Resources выбрать **Include → Specific account** и свой аккаунт. Для этого Worker без доменных routes, KV, R2 и баз данных соответствующие дополнительные права не нужны. Токен позволяет изменять Workers выбранного аккаунта; это не доступ только к одному файлу. Желательно ограничить срок, например семью днями на настройку. Не использовать Global API Key.
3. Сохранить токен непосредственно в GitHub: репозиторий → **Settings → Secrets and variables → Actions → New repository secret**. Значение в чат не отправлять. Добавить записи:

| GitHub Actions Secret | Что указать |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | Созданный ограниченный токен Cloudflare |
| `CLOUDFLARE_ACCOUNT_ID` | 32-символьный Account ID своего аккаунта Cloudflare |
| `SIDJ_ADMIN_TOKEN` | Необязательно: собственный пароль панели, если нужен ручной доступ через `/setup` |
| `SIDJ_TELEGRAM_BOT_TOKEN` | Уже настроенный действующий токен бота — сохранить существующий |
| `SIDJ_TELEGRAM_CHAT_ID` | Уже настроенный ID личного чата — сохранить существующий |

Обязательны только две новые записи: `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`. Если `SIDJ_ADMIN_TOKEN` не задан, workflow вычисляет отдельный служебный ключ HMAC-SHA256 из токена бота с меткой `B/S-SiDj-admin:v1`, сохраняет его в Secret Worker и использует для операций из GitHub. Ключ отличается от секрета входящих Telegram-запросов и не выводится в журналы. Ручная панель `/setup` при этом не нужна. Для доступа к ней можно заранее задать собственный `SIDJ_ADMIN_TOKEN` (32–128 символов `A-Z a-z 0-9 _ -`); после изменения нужен повторный `deploy` для синхронизации. Пароль Cloudflare или Google для этого не используется.

После настройки временный токен Cloudflare можно отозвать: работа webhook-бота от него не зависит, но будущим развёртываниям снова потребуется доступ.

## Порядок запуска

Открыть **Actions → SiDj Cloudflare - manual operations → Run workflow**, ветка **main**. Проверить тариф и отметить подтверждение **Workers Free**. Без этого облачные операции не выполняются.

По умолчанию выбрано `deploy`. Название запуска показывает выбранную операцию. Если запрос отклонён, журнал различает Cloudflare API и адрес Worker; для API выводятся только числовые коды ошибок без текста ответа и секретов.

HTTP-клиент явно представляется как `B/S-tech-SiDj-operations/1.0` со ссылкой на исходный репозиторий. Это важно для стандартных проверок Cloudflare: при первом развёртывании код и секреты были успешно опубликованы, но проверка адреса со стандартным `Python-urllib` получила HTTP 403 / 1010. Идентифицированный служебный клиент получил HTTP 200; имитация браузера и отключение защиты не используются.

1. `deploy` — проверяет код, разворачивает `bs-tech-sidj`, вычисляет его HTTPS-адрес по поддомену аккаунта, применяет три секрета Worker через stdin. **Webhook пока не меняется.** Адрес Worker появится в журнале; секретные значения туда не выводятся.
2. `status` — проверяет личный чат, имя Telegram-бота и текущее подключение webhook.
3. `activate` — сначала проверяет HTTP 403 для неподписанного входящего запроса и проверяет панель владельца, затем включает webhook с сохранением очереди. Эта операция и старый опрос используют одну группу concurrency, поэтому запущенный job опроса сначала закончится.
4. Проверить настоящие команды, нажатия кнопок, файлы, SHA-256, фактическую скорость и метрики Cloudflare. Только после успеха отключить старый workflow `sidj-telegram-commands.yml`. Workflow уведомлений оставить включённым.

`rollback` удаляет только webhook этого Worker без сброса очереди. После успешной миграции у старого `sidj-telegram-commands.yml` оставлен только ручной запуск. Для постоянного отката сначала восстановить в нём расписание `3-58/5 * * * *`, затем выполнить `rollback`: пока webhook подключён, Python-обработчик безопасно выходит. Для разового опроса после `rollback` можно вручную запустить старый workflow. При отсутствии подтверждения сетевой операции сначала выполнить `status`, а не многократно повторять `activate`.

Доступ только к выбранному аккаунту и проверка Workers Free задаются владельцем: workflow не читает платёжные данные, не изменяет тариф и не создаёт платные очереди/хранилища. Наличие файлов workflow в GitHub не означает, что Cloudflare уже подключён. Нужны реальные секреты и успешный запуск.

## Проверка без доступа к Cloudflare

```bash
python3 -m unittest discover -s automation -p 'test_sidj_cloudflare.py' -v
```

Тесты проверяют отсутствие секретов в аргументах/выводе, передачу secret bulk через stdin, отказ от перенаправлений с Authorization, ограничения адреса, явное подтверждение тарифа, подготовку активации и отсутствие переключения webhook на этапе deploy. Реальные права токена, тариф и доставку Telegram подтверждают после ввода секретов.

`npm test` также запускает настоящий workerd через Miniflare: проверяет исходящий запрос и отказ от перенаправления с заголовком Authorization. В runtime Cloudflare нужен `redirect: manual` и явная проверка 3xx; браузерный `redirect: error` здесь не поддерживается.

После активации доступен явный интеграционный тест `python3 automation/sidj_cloudflare_smoke.py --send-test-messages`. Он требует те же секреты и подтверждение Workers Free, проверяет панель и подключённый webhook, затем отправляет тестовые команды только в настроенный личный чат. Записывает время обработки и не выводит секреты. Это синтетические подписанные обновления; реальные нажатия кнопок и полученные файлы проверяются отдельно.

Официальные источники: [Cloudflare API Tokens](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/), [получение поддомена Workers и требуемое право Workers Scripts](https://developers.cloudflare.com/api/resources/workers/subresources/subdomains/methods/get/), [группы concurrency GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

## Чтение CPU и квот

Для аналитики используется отдельный GitHub Secret CLOUDFLARE_ANALYTICS_TOKEN: право Account → Account Analytics → Read только для выбранного аккаунта. Никаких прав редактирования или доступа к оплате не требуется. Account ID берётся из существующего CLOUDFLARE_ACCOUNT_ID. Значения токенов не отправляются в чат.

Открыть Actions → SiDj - Worker metrics (read only) → Run workflow на main. Workflow запускает тесты обработки данных и читает GraphQL Analytics без развёртывания, изменений webhook и доступа к токену Telegram. Отчёт содержит только агрегированные показатели этого Worker, общий счётчик вызовов для суточной квоты и время по Москве; Account ID и токен в него не выводятся. В публичном репозитории агрегаты в журнале Actions доступны читателям, поэтому содержимое запросов, пользователи и другие Worker по именам не запрашиваются.

Скрипт проверяет единицы CPU по описанию схемы и не объединяет процентили разных групп. Если единицы не подтверждены, выводит исходные значения с явной пометкой. Пустая выборка не считается нулевым CPU. P99 — не максимум; errors считает runtime failures, а не все HTTP-ошибки. Суточная квота Free сбрасывается в 03:00 МСК. Метрики могут быть выборочными и задерживаться; текущий тариф подтверждается владельцем, биллинг этим токеном не читается.

## Автоматическое обновление после миграции

Помимо ручного `sidj-cloudflare.yml` в репозитории подготовлены отдельные workflow:
- `sidj-worker-autodeploy.yml` — проверка и код-only развёртывание из `main` только при изменении Worker/каталога. Webhook, Telegram Secrets и ручной резерв не переключаются. Без действующего `CLOUDFLARE_API_TOKEN` развёртывание **не** состоится, но опубликованный Worker продолжит работу. Владелец подтвердил тариф Workers Free в день миграции; любые последующие изменения тарифа проверяются отдельно.
- `sidj-worker-monitor.yml` — 15-минутный независимый контроль доступности Worker, адреса webhook и статуса аналитического токена. Уведомления о подтверждённом событии и восстановлении идут только в личный чат через прежний Telegram Secret. Повторы подавляются через кэш Actions, не через коммиты в `main`.

Изменения документации и файлов состояния монитора не запускают публикацию. GitHub Actions не гарантирует точное время выполнения cron. Для локальных тестов монитора: `python3 -m unittest discover -s automation -p 'test_sidj_worker_monitor.py' -v`.

**Разные виды отката:** ручная операция `rollback` в `sidj-cloudflare.yml` удаляет webhook, тогда как откат **кода Worker** выполняется через историю Deployments Cloudflare или новой публикацией исправленного кода. Перед обоими типами отката проверять, что меняется именно нужный компонент. Фактическое состояние токенов нельзя вывести из наличия GitHub Secrets: при отказе доступа нужно обновить токен в защищённом интерфейсе.
